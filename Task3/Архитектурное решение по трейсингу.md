### **Пользовательские сценарии:**<br>
**1. Пользователь создаёт заказ через интернет магазин (Internet-shop).**
   Клиент (Internet-shop)
- (Internet-shop) Пользователь создаёт заказ на производство изделия (INITIATED);
- (Internet-shop) Загружает файл с 3D моделью изделия/генерирует 3Д файл на сайте (FILE_UPLOADED);
- (Internet-shop) Отдаёт заказ в работу (SUBMITTED);
  Оператор (MES)
- (MES) Система посчитала стоимость заказа (PRICE_CALCULATED);
  Продавец отражает подтверждение стоимости заказа
- (CRM) Заказ подтвержден (MANUFACTURING_APPROVED);<br>
  Оператор (MES)
- (MES) Оператор взял заказ в работу (MANUFACTURING_STARTED);
- (MES) Оператор выполнил заказ (MANUFACTURING_COMPLETED);
- (MES) Оператор начал упаковывать заказ (PACKAGING);
- (MES) Заказ отправлен покупателю (SHIPPED);
- (CRM) Заказ завершен, закрывается после получения сообщения от транспортной компании (CLOSED).

Обработка заказа может прерваться на этапах:
* генерации (сбора через конструктор) 3Д файла. Сбор файла модели через конструктор может расходовать вычислительную мощность процессора (CPU) и оперативную память (RAM).
* не удаётся загрузить файл в s3 хранилище
* при сохранении данных в базу данных Internet-shop возникают ошибки
* расчет стоимости заказа может отнимать много ресурсов CPU, RAM;
* по трейсу будет видно сколько времени в CRM подтверждали заказ (после расчета стоимости).
* ошибки отправки сообщения в очередь - отправка статуса MANUFACTURING_APPROVED в CRM.
- записи/чтения данных в/из mes_db;

### **Мотивация:**<br>
По трейсам можно будет отслеживать путь заказа через все компоненты системы, быстрее находить причины сбоев. 

**Бизнес-метрики, на которые повлияет внедрение трейсинга:**<br>
**1. Время диагностики инцидентов.**<br>
   **Влияние на метрику:** Сокращается время поиска первопричины ошибки, благодаря возможности проследить выполнение запроса между сервисами.<br>
   **Как измерять:** Среднее время от обнаружения инцидента до восстановления работоспособности.<br>
**2. Стоимости эксплуатации и поддрежки.**<br>
   **Влияние на метрику:** Сокращаются трудозатраты инженеров на расследование проблем и поиск узких мест; появляется возможность точнее оптимизировать использование ресурсов.<br>
   **Как измерять:** Часы инженерной работы на инциденты, затраты на инфраструктуру и стоимость обработки единицы нагрузки.<br>

**Технические метрики, на которые повлияет внедрение трейсинга:**<br>
**1. Задержка обработки запросов (latency p95/p99).**<br>
   **Влияние на метрику:** Упрощается выявление медленных сервисов, вызовов к бд и внешним api, что позволяет оптимизировать критические участки системы.<br>
   **Как измерять:** Перцентили p95/p99 времени ответа до и после внедрения трейсинга.<br>
**2. Частота ошибок (error rate).**<br>
   **Влияние на метрику:** Ускоряется выявление источников ошибок и каскадных сбоев, что помогает быстрее устранять дефекты и снижать количество повторных инцидентов.<br> 
   **Как измерять:** Доля запросов с ошибками от общего числа запросов, а также частота повторных инцидентов.<br>

### **Предлагаемое решение:**<br>

Трейсинг будет внедрен с помощью OpenTelemetry (OTel) / Jaeger .
OpenTelemetry отвечает за сбор и генерацию данных (трассировок, метрик), а Jaeger - сервис для их хранения, анализа и визуализации.
Этапы:
1. Инструментирование (Приложение).
   Внутри кода каждого сервиса будет работать OpenTelemetry SDK. SDK формирует спаны (отрезки работы) и собирает их в единый трейс.
2. Передача (Экспорт).
   По протоколу OTLP (OpenTelemetry Protocol) данные в бинарном или JSON-виде отправляются из приложения наружу.
3. Конвейер Jaeger v2 (Прием и обработка).
- Receiver (Приемник): Встроенный в Jaeger модуль слушает порты 4317 / 4318.
- Processor (Обработчик): Выполняет пакетную группировку (batching) и фильтрацию (sampling) данных.
- Exporter (Экспортер): Сохраняет обработанные трейсы в выбранное хранилище.
4. Хранение (Storage).
   Данные оседают в постоянном хранилище (Elasticsearch).
5. Визуализация (UI).
   Пользователь заходит в Jaeger UI (обычно на порт 16686), который через компонент Jaeger Query запрашивает данные из базы и рисует понятные waterfall-диаграммы прохождения запроса.

В "Jewerly Store System" каждый сервис нужно доработать - внерить OpenTelemetry SDK для пробороски трейсов.
Развернуть Jaeger, OpenTelemetry Collector и развернуть базу (Elasticsearch).

### **Компромиссы:**<br>

Если у систем закрыт исходный код, то собственными силами не получится внести нужные изменения. Вносить изменения через стороннюю организацию часто бывает долго и дорого. В таком случае можно запланировать добавления трейсинга с подрядчиком. Рассмотреть другие способы observability (временно).

Нужно реализовать пункты из Task1 (Инициативы, необходимые для устранения нежелательных ситуаций) и следить за работоспособностью системы. Возможно хватит логов/метрик/алертов для диагностики деградации сервисов.
